# Internationalisation

Two locales from day one - `en` and `pl` - so that adding a third is a file rather than a
project. [ADR-0008](../adr/0008-i18n-from-the-start.md) explains why retrofitting this is
the expensive option.

**Never hard-code a user-facing string.** Every one goes through a key, on both sides, and
both sides are held to locale parity: the backend refuses to start with a key in one
catalogue and not the other, and `make i18n-check` (in `make check`) compares every
catalogue and the landing pages. The symptom otherwise is a raw key rendered in production,
to exactly the users who read that language.

---

## Where catalogues live

| Side | Path | Shape |
|---|---|---|
| Backend, the kernel | `backend/kernel/i18n/messages.{en,pl}.json` | flat, dotted lowercase keys; `%name%` placeholders |
| Backend, a module | `backend/internal/module/<name>/i18n/messages.{en,pl}.json` | the same |
| Frontend, a layer | `<layer>/i18n/locales/{en,pl}.json` (+ `.ts`) | `@nuxtjs/i18n`'s `<locale>.json`; `{name}` placeholders |
| Landing pages | `landing/content/{en,pl}/<page>.md` | one file per page per language ([`landing.md`](landing.md)) |

Each side keeps the convention native to its own tooling rather than a unified one - the
discovery in both cases is somebody else's, and fighting it costs more than the asymmetry
does. No central file registers a catalogue: a backend module embeds its `i18n/` directory
(`Locales:` in `module.go`), and a frontend layer names its files in its own
`nuxt.config.ts`.

### The `.ts` wrapper, and why it exists

```ts
// ui-kit/i18n/locales/en.ts
import messages from './en.json'

export default messages
```

`@nuxtjs/i18n` is pointed at the `.ts`, never the `.json`. Registering the JSON directly
makes Vite's json plugin wrap the output of the i18n transform in `JSON.parse()`, and the
landing site - the one app that renders on the server - dies at boot with
`Unexpected token 'c', "const reso"`. The data stays in the `.json` so the parity check can
read it; the loader points at the wrapper.

Do not set `langDir`. `@nuxtjs/i18n` already resolves `<layer>/i18n/locales`, and overriding
it produces `i18n/i18n/en.json` - a path that silently matches nothing.

## Frontend

```vue
<script setup lang="ts">
const { t } = useI18n()
</script>

<template>
  <h1>{{ t('example.title') }}</h1>
  <p>{{ t('example.archived', { count: archived }) }}</p>
</template>
```

A module layer contributes its own catalogue next to its own pages, and `@nuxtjs/i18n`
merges the `files` arrays across layers by locale code. Keys are namespaced by module for
that reason: two layers contributing `title` would be one merge away from an argument.

The two SPAs use `strategy: 'no_prefix'` (from `ui-kit/nuxt.config.ts`) and remember the
choice in the `open_enu_locale` cookie, `SameSite=None` - never `Strict`: the landing site
links into the app across subdomains, and a strict cookie is dropped on exactly that
navigation, resetting the language every time somebody signs in. The landing site gives
each language its own URL instead. Before anyone has chosen, every app starts in
`DEFAULT_LOCALE` (`.env`, written into each app's `.env` by `make env`) - **never in the
browser's language**. `@nuxtjs/i18n` cannot keep a cookie without also guessing from the
browser, so `detectBrowserLanguage` is off everywhere and `ui-kit/app/plugins/locale.client.ts`
keeps the cookie. `e2e/tests/locale.spec.ts` proves both halves with a browser that prefers
the other language; the rest of the suite starts as someone who chose English.

Nothing lints a template for raw text; a sentence typed into a component is caught in
review, not by a check.

## Backend

```go
const keyArchived i18n.Key = "example.error.archived"

if !canEdit(old) {
	return project{}, httpx.Forbidden(keyArchived) // the envelope's message, translated per request
}
```

An `*httpx.Error` carries an `i18n.Key`; `httpx.WriteError` translates it into the
envelope's `message` in the request's locale. Where text is produced outside a response - a
mail - the code calls `svc.I18n.Translate(locale, key, params)` itself.

What holds the catalogues together, all at start-up (`module.NewRegistry`, and so in
`openenu modules` and every process):

- a key present in `messages.en.json` and absent from `messages.pl.json`, or the reverse -
  `make selftest` plants one and expects `openenu modules` to fail;
- a key two modules both define - keys are namespaced by module;
- a value that is not a string (a nested object is a key that was meant to be dotted), and
  a key that is not dotted lowercase;
- a catalogue for a locale that is not enabled, and an enabled locale whose catalogue is
  missing.

And at build time, the `rawstring` analyzer refuses a string constant used as an
`i18n.Key` that is not dotted lowercase - in a call, a conversion or a declaration - so
`httpx.NotFound("Project not found.")` does not pass `make check`.

### Which language a response speaks

`httpx.Locale` (`backend/kernel/httpx/locale.go`) runs twice in the chain. Before the auth
middleware it resolves from `Accept-Language` alone, so the middleware's own 401 is
translated. After it, it asks, in order:

1. every module's `Locale` preference (`Module.Locale`, an `httpx.LocalePreference`), a
   module's before those of the modules it depends on - the first that names an enabled
   locale wins. Two modules contribute: Identity the signed-in person's saved locale, Tenant
   the workspace's default. Identity depends on Tenant, so a person's own choice outranks the
   workspace's default, which is always set;
2. `Accept-Language`, narrowed to the enabled locales;
3. the catalogue's default - `APP_DEFAULT_LOCALE`, which compose sets from `DEFAULT_LOCALE`.

`Content-Language` on the response says what was chosen. A module influences the choice by
contributing a preference, never by reading a header itself.

### Things that are written once and read later

A notification row stores a **type and arguments**, never a sentence:

```go
d.notifier.ToTenant(ctx, del.TenantID, NotificationDeliveryFailed, map[string]any{
	"event": del.EventName, "url": e.URL, "attempts": after.Attempts,
})
```

The declaration (`notification.Definition`) carries `TitleKey` and `BodyKey`; the registry
refuses one whose keys the module's catalogue lacks. The feed returns the keys and the
arguments (`titleKey`, `bodyKey`, `context`) and the client translates them in the reader's
language, so the same keys live in the Notification layer's frontend catalogue too. Storing
prose would freeze the message in whatever language the worker happened to be running in -
which is usually the language of nobody who will read it.

The same rule applies to mail: rendered at send time, in the recipient's saved locale, or
the default when there is none.

## Adding a locale

1. **Frontend:** add `{ code: 'de', language: 'de-DE', files: ['de.ts'] }` to
   `ui-kit/nuxt.config.ts`, and a `de` entry to the `locales` of every app and every module
   layer's `nuxt.config.ts`; beside every `en.json`, a `de.json` and its `.ts` wrapper.
2. **Backend:** a `messages.de.json` beside every `messages.en.json` - the kernel's and every
   module's - and `de` in `APP_LOCALES` (`en,pl` unless set, read in
   `backend/cmd/openenu/platform.go`; pass it to the three backend containers through
   compose). The registry refuses to start until every catalogue is there. Identity's
   registration and profile accept exactly the enabled locales and refuse anything else -
   deliberately, because a setting that "saves" and then does not apply is a bug report
   nobody can reproduce.
3. **Landing:** `landing/content/de/` with every page, and a `pages_de` collection in
   `landing/content.config.ts`.
4. Add `de` to `LOCALES` in `scripts/dev/check-i18n.sh`. Then `make i18n-check` names every
   key and page still missing, on both sides, and `openenu modules` the backend's.
